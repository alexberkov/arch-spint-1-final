### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает отправку запросов на устройства, установленные на обогревательных приборах в домах пользователей, тем самым предоставляй контроль над отоплением.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- Система получает данные о температуре через регулярные запросы, отправляемые на датчики, установленные в домах пользователей.

### 2. Анализ архитектуры монолитного приложения

- *Язык программирования*: Go
- *База данных*: PostgreSQL
- *Архитектура*: Монолитная - все компоненты системы сосредоточены в рамках одного сервиса и разделяют хранилище данных
- *Взаимодействие*: Синхронное, все операции выполняются последовательно
- *Масштабируемость*: Ограничена, монолитное приложение можно масштабировать только целиком, а не отдельные его части
- *Развертывание*: Требует остановки всего приложения при вснесение любых изменений в одну из функций приложения

### 3. Определение доменов и границы контекстов

- *Домен "Управление устройствами":* Отвечает за регистрацию устройств и изменение их состояния (управление отоплением)
- *Домен "Мониторинг устройств":* Отвечает за сбор данных с устройств и предоставление информации пользователям

### **4. Проблемы монолитного решения**

- Отсутствие гибкости и высокий риск ошибок: изменение в одной части приложения влияют на работу всей систему и могут вызвать непредвиденные ошибки
- Трудности тестирования и развертывания: При каждом внесении изменений нужно тестировать все приложение целиком и полностью останавливать сервис для развертывания
- Ограничения масштабирования: Монолитное приложение нельзя масштабировать по частям
- Проблемы разработки новых функций: При текущей архитектуре добавление новых функций затруднено, поскольку нужно детально продумывать их взаимодейстие с другими частями приложения

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
